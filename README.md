# JaesolOS / Jaesol Stack

> **Because frontend and backend weren't full-stack enough.**

**Project status (2026-10-28): RISC-V reboot planned; implementation not started.**  
**Existing artifact: legacy x86 Phase 1 — reported bootloader + VGA text output.**  
**Target board: Terasic DE10-Standard (Cyclone V SoC).**

Jaesol Stack is a hobby project to serve a real web page from a computer built around an FPGA soft-core CPU, a minimal operating system, and a tiny HTTP server. It optimizes for **working demos, feasibility, and fun**, not comprehensive OS education or implementing everything from scratch.

*I wanted to host my personal website. So naturally, I decided to build the computer first.*

## End-to-end objective

```text
Browser ──HTTPS──> Existing Linux host / Caddy reverse proxy
                            │ HTTP over a private network
                            ▼
                   JaesolCaddy (HTTP app)
                            ▼
                    JaesolOS (RISC-V)
                            ▼
                 FPGA soft-core RISC-V SoC
                            ▼
                   Terasic DE10-Standard
```

**Definition of done:** An external browser loads an actual HTTP response generated by JaesolCaddy running under JaesolOS on the FPGA-fabric RISC-V CPU. The existing Linux reverse proxy may terminate TLS and route requests, but must not manufacture the origin HTML. A dynamic uptime or request counter can prove that the FPGA is responding. First deploy under a separate demo hostname (proposed: `stack.jaesolahn.com`); do not disrupt the existing site.

## Proposed implementation

- **Architecture:** RV32 RISC-V bare-metal/freestanding kernel (initial target: QEMU `virt`). Treat the FPGA memory map, startup, interrupts, console, and NIC as board-specific ports.
- **Networking:** QEMU `virtio-net` for the virtual prototype; portable lwIP for ARP/IPv4/ICMP/TCP; a separate FPGA-side NIC/transport backend later.
- **HTTP:** JaesolCaddy v0.1 is a small HTTP/1.x static/dynamic response application. **It is not the Go-based Caddy server**, nor a port of the complete Caddy runtime.
- **FPGA:** Investigate LiteX + a proven RV32 soft-core (e.g. VexRiscv), but first validate exact DE10-Standard target support, Quartus version, SDRAM, and pinout. A custom board target or a different SoC toolchain may be necessary.
- **Deployment:** Existing Linux Caddy terminates TLS and proxies only approved routes to the experimental OS; keep experimental services isolated from the public internet.

### DE10-Standard networking caveat (important)

The on-board RJ45 / Gigabit Ethernet PHY is connected to the **Cyclone V HPS (ARM)** Ethernet MAC, not directly to a fabric soft-core. Therefore a generic LiteEth fabric MAC cannot simply be mapped onto that RJ45 connector. Select and test **one** of:

1. **HPS-assisted network bridge:** ARM HPS forwards frames/requests via a defined FPGA/HPS transport (for example, an AXI/shared-memory interface) to JaesolOS running on the FPGA RISC-V CPU. This is a practical demo route, but label the HPS intermediary honestly.
2. **External FPGA-side Ethernet interface:** use a compatible GPIO/HSMC expansion solution such as an SPI Ethernet controller with a real MAC/PHY; keep TCP/IP processing in lwIP on the RISC-V CPU. Verify electrical compatibility and driver effort before purchasing.
3. **Temporary dev-only UART/host bridge:** useful for debugging but **does not meet the final Ethernet-demo definition of done**.

Do not claim the DE10-Standard directly exposes its built-in PHY to fabric without documented evidence.

## Milestones / acceptance tests

1. **P0 — Archive + baseline:** inspect repository, preserve all x86 files, reproduce or diagnose historical boot; add reproducible test commands.
2. **P1 — RISC-V first boot:** boot a minimal RV32 kernel under QEMU `virt`, emit a deterministic UART boot banner; no OS scheduler/POSIX required.
3. **P2 — Network reachability:** `virtio-net` RX/TX + lwIP integration, ARP/ICMP exchange verified with packet capture and automated tests.
4. **P3 — First HTTP 200:** JaesolCaddy responds to a browser/`curl` request with real HTML and at least one dynamic counter; verify a complete TCP exchange.
5. **P4 — Public demonstration:** isolated internal HTTP origin exposed through existing Linux Caddy with TLS at a separate hostname; original website remains unchanged.
6. **P5 — DE10-Standard boot:** FPGA-fabric RISC-V core boots JaesolOS, uses verified on-board memory and UART; record synthesis/toolchain versions.
7. **P6 — FPGA network demonstration:** FPGA-hosted JaesolOS/JaesolCaddy replies to external requests using the tested HPS bridge or FPGA-side Ethernet path; capture reproducible logs/video.

Advance only after a demonstrated milestone. Prefer a small running prototype to building a complete operating system.

## Development workflow (Claude Code + human review)

- Claude Code: investigate hardware support, implement small scoped tasks, run real tests, document traces and failures, suggest small reviewable commits.
- Human: decide architectural tradeoffs and hardware deployment; approve risky operations.
- GPT/other reviewer: sanity-check requirements, interface contracts, tests, and scope.
- Separate **verified**, **planned**, and **assumed** statements. Never label unexecuted code as working.
- No destructive rewrite of legacy code; no credential commits, DNS changes, firewall changes, FPGA flashing, or modifications to production services without explicit approval.
- Begin with **P0 + DE10-Standard feasibility assessment**, not a mass generation of untested source files.

## Legacy x86 JaesolOS — original Phase 1

The original repository began as a hobby x86 OS for learning. Its README reported:

- Multiboot-compliant kernel launched through GRUB
- 32-bit protected-mode assembly entry
- VGA text-mode driver (80×25, 16 colors)
- Boot log/system information printed on screen

The *historical* source layout was documented as follows; individual file presence and the current build have **not** been revalidated during the planning update:

```text
boot/boot.asm
boot/linker.ld
kernel/kernel.c
kernel/vga.c
include/vga.h
iso/boot/grub/grub.cfg
Makefile
```

Historical Ubuntu/Debian dependency example:

```bash
sudo apt install build-essential nasm qemu-system-x86 \
  grub-pc-bin grub-common xorriso mtools
make
qemu-system-i386 -cdrom JaesolOS.iso
```

These commands apply to the **legacy x86 experiment**, not the future RV32 build; they should be tested before claiming the old version still builds.

Historical roadmap (superseded): GDT/IDT and interrupts → physical memory/paging → scheduler → VFS/syscalls/user shell.
